# Forms

Create and edit forms use the shared action panel for destructive, cancel, and primary actions. On Android, the panel remains visible and docks above the software keyboard while a field is focused; other sticky page actions continue to hide so they do not obstruct the focused field.

In the native Android and iOS apps, pressing Cancel while a form field's keyboard is visible requests native keyboard dismissal without directly blurring the web field. Pressing Cancel while the keyboard is hidden follows the form's normal cancel behavior.

Cancel exits immediately when a form is unchanged. After any field differs from its initialized or saved value, Cancel asks the user to confirm that they want to discard their unsaved changes.

After a form save succeeds, the shared bottom snackbar identifies both the saved record type and its name, for example `Task “Morning walk” saved.` Names are collapsed to one line and shortened when necessary. Untitled reflections use the beginning of their body, and form-like log actions use the tracker or image-log label. This confirmation survives route navigation and is shown for create and edit flows, reusable dialogs, and in-session settings forms.

The shared number pad keeps zero centered in its bottom row and Delete on the right. Decimal inputs place the decimal point on the left; whole-number inputs leave that position empty so the remaining keys do not shift.

Emoji fields use the shared `EmojiSelector` component. Its outlined button shows the selected emoji and human-readable icon name, then opens a searchable, full-screen, vertically scrollable dialog containing every standard Unicode emoji and skin-tone variant. The dialog keeps its controls clear of native safe areas. The search field receives focus when the dialog opens. Results use human-readable labels and a virtual list so only the visible options are mounted. The emoji dataset is loaded the first time a selector without a saved value opens, and saved values preload it so their names can be shown; loaded data is reused by every selector instance.

Exercise relationship fields use the shared `ExerciseSelector` component and store the stable RepDB exercise id on their entity. The outlined button shows the selected exercise's 64×64 image, English name, and body part. It opens a full-screen scrollable dialog grouped by body part, with a persistent active-category header and 128×128 images. The selected image shows a neutral animated placeholder while loading and honors reduced-motion preferences; virtualized result images use native eager images so their browser-cached content remains stable while scrolling. Each result shows a three-bar Easy, Intermediate, or Advanced indicator directly below its description; filled bars use the semantic difficulty color and unfilled bars remain grey. Search covers category, equipment, body part, localized name, primary muscles, and secondary muscles without showing a separate result count. The empty-query browse view is grouped by body part. Query results are flat and sort by matching primary-muscle position then name, secondary-muscle position then name, body part then name, name, then category or equipment. The queries `ab`, `abs`, `abdominal`, and `abdominals` also return exercises whose body part is Core or whose muscle metadata references the obliques. The queries `chest` and `pecs` also return exercises whose muscle metadata references the pectoralis. Body-part headers and results share a virtual list so only nearby exercise cards and images are mounted. English is the default locale; German and Spanish are also supported through the component's `locale` prop. The catalog loads lazily from the bundled RepDB free-tier snapshot, is reused between selector instances, and its static images are included in the offline web shell. Dataset attribution remains visible at the bottom of the dialog.
